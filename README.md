# Webhook Reliability API

A backend API built with FastAPI, SQLAlchemy, and PostgreSQL for managing customers, subscriptions, and subscription cancellation events.

The project models a simplified webhook reliability system. Customers can subscribe, cancel subscriptions, and generate persistent `subscription.cancelled` events.

> V1 does not send outbound HTTP webhook requests. It focuses on reliably creating and storing events generated by real subscription actions.

## Features

- Create and retrieve customers
- Prevent duplicate customer emails
- Prevent duplicate webhook URLs
- Start subscriptions
- Allow only one active subscription per customer
- Preserve subscription history
- Cancel subscriptions
- Automatically create `subscription.cancelled` events
- Prevent deleting customers with active subscriptions
- Delete customer-related subscription and event data
- List and delete events
- PostgreSQL persistence
- Automated API tests with pytest

## Data Model

### Customer

- `id`
- `name`
- `email`
- `webhook_url`

Both `email` and `webhook_url` must be unique.

### Subscription

- `id`
- `customer_id`
- `status`
- `subscribed_at`
- `cancelled_at`

A customer may have multiple subscriptions over time, but only one active subscription at a time.

### Event

- `id`
- `event_type`
- `customer_id`
- `subscription_id`
- `created_at`

Currently supported event type:

```text
subscription.cancelled
```

The event is automatically generated when a subscription is cancelled.

## API Endpoints

| Method | Endpoint | Description |
|---|---|---|
| POST | `/customers` | Create a customer |
| GET | `/customers/{customer_id}` | Get a customer |
| DELETE | `/customers/{customer_id}` | Delete a customer |
| POST | `/customers/{customer_id}/subscriptions` | Start a subscription |
| GET | `/customers/{customer_id}/subscriptions/active` | Get active subscription |
| GET | `/customers/{customer_id}/subscriptions` | Get subscription history |
| POST | `/subscriptions/{subscription_id}/cancel` | Cancel a subscription |
| GET | `/events` | List events |
| DELETE | `/events/{event_id}` | Delete an event |

## Important Business Rules

- Customer email addresses must be unique.
- Customer webhook URLs must be unique.
- A customer can have only one active subscription at a time.
- A cancelled customer subscription remains in subscription history.
- A customer may subscribe again after cancellation.
- Cancelling a subscription automatically creates a `subscription.cancelled` event.
- A customer with an active subscription cannot be deleted.
- Deleting an eligible customer also removes related subscriptions and events.

## Setup

### 1. Clone the repository

```bash
git clone <repository-url>
cd webhook_reliability
```

### 2. Create a virtual environment

```bash
python3 -m venv .venv
source .venv/bin/activate
```

### 3. Install dependencies

```bash
python -m pip install -r requirements.txt
```

### 4. Create the PostgreSQL database

Start PostgreSQL:

```bash
brew services start postgresql@17
```

Open PostgreSQL:

```bash
psql postgres
```

Create the development database:

```sql
CREATE DATABASE webhook_reliability_db;
```

For automated tests:

```sql
CREATE DATABASE webhook_reliability_test_db;
```

Exit:

```text
\q
```

## Run the API

```bash
python -m uvicorn main:app --reload
```

Open Swagger documentation:

```text
http://127.0.0.1:8000/docs
```

## Run Tests

Make sure PostgreSQL is running and the test database exists.

Then run:

```bash
python -m pytest -v
```

## Example Workflow

1. Create a customer.
2. Start a subscription.
3. Attempting to create another active subscription returns `409 Conflict`.
4. Cancel the active subscription.
5. A `subscription.cancelled` event is automatically created.
6. The customer may create a new subscription later.
7. Historical subscriptions remain available.

## Current Scope

This is the first version of the project.

The application currently records webhook-style events but does not yet deliver outbound HTTP webhook requests to customer URLs.

Future versions may add webhook delivery, retry handling, delivery status tracking, migrations, and more advanced reliability mechanisms.
